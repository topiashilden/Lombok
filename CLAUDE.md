# Solvo (repo: Lombok) — Junction 2026 hackathon project

## Goal
Solvo, tagline "Fixed costs aren't fixed." A mobile-first money coach for S-Pankki customers that doesn't just show where the money went, it **cuts fixed costs**: it reads the e-invoices that already reach the bank, the AI extracts supplier, price, base fee, consumption and contract end date, shows how much they overpay, and simulates switching the contract with the user's approval. The user never has to photograph or upload anything. Challenge: S-Pankki "Personal Economic Trainer" (Junction 2026). Full plan, demo script, risks and schedule: `PLAN.md` (in Finnish, version 2; it is the source of truth for scope). The draft submission has been sent.

Deadline: draft submission Fri 13.11. 23:59, FINAL Sun 15.11. 10:00, live peer review Sun 10:30–13:00. A working demo beats clean code.

## Demo in one line
Three baskets (1 fixed and regular, 2 fixed and irregular, 3 everyday leakage) and one number, "how much can I safely spend this week?". Solvo has already read the e-invoices and identified each contract → open the electricity contract (AI-extracted fields) → compare → overpay ~€240/yr → one-tap approved switch → safe-to-spend goes up. Coach chat answers questions like "how much did I spend on taxis?" from the real S-Pankki data.

## Scope (from PLAN.md)
- Electricity first. Phone and internet only if time remains.
- Switching is simulated. The pitch explains how a real switch would work (new supplier cancels the old contract).
- No insurance comparison (needs insurance-agent registration). Insurance appears only in the spend basket.
- No native app: a web app that works well in a mobile browser.
- No bill photos and no uploads. S-Pankki has no open API in this challenge, so the demo uses synthetic Finvoice e-invoices linked to the dataset's Utilities payments (in production they would come from the bank's real e-invoice stream).
- Every extracted e-invoice field is shown to the user and editable. Pre-test the demo e-invoices.
- The user approves every switch; the AI never acts alone.
- Competition rules: all code written at the event, MIT licence, synthetic or challenge data only, no existing company.

## Stack
- Next.js (App Router, TypeScript), Tailwind, shadcn/ui. Mobile-first layout.
- Gemini API for reading e-invoices (Finvoice → structured fields) and the coach chat. Key in `.env.local`.
- No auth: hardcoded demo customer. No database planned: 1–3 demo customers preprocessed from the S-Pankki data into static JSON under the app. Add Supabase only if asked.
- Synthetic Finvoice e-invoices for the demo customer(s), tied to their Utilities rows.
- Electricity spot price: a free API (porssisahko.net or ENTSO-E). Supplier prices: a hand-maintained table first, Context.dev later (optional bonus). ElevenLabs voice is an optional wow-factor.
- Deployed on Vercel from `main`

## Data (S-Pankki challenge dataset)
Cloned from https://github.com/hackjunction/Junction-2026-S-pankki into `data/s-pankki/` (gitignored, never commit it).
- `tx_junction_transactions.csv`: ~346 MB via Git LFS (`customer_id`, `bank_account_id`, `tx_date`, `tx_timestamp`, `category`, `tx_amount_eur`, `balance_after_eur`, `transaction_type`, `merchant_id`, `mcc_code`). Downloaded and checksum-verified. 3.63M rows, 5,100 customers, 2024-10-01 to 2026-09-30, 515 merchants, 36 MCC codes (~78% of rows have one). Categories: Groceries, Restaurants, Transportation, Utilities, Entertainment, Health, Salary, Home & Tech, Housing, Lifestyle, Travel, Invest Deposit, Other Income, Salary Sweep, Invest Withdraw. Debits are negative `tx_amount_eur`. If the file ever starts with `version https://git-lfs`, it is only the pointer again.
- `tx_customers_junction.csv`: 5,100 customers (`customer_id`, `customer_postal_code`, `customer_age`)
- `mtg_*.csv`: mortgage application history and outcomes (not needed for the coach)
- CSVs start with a UTF-8 BOM: read with `utf-8-sig`.
- Preprocess 1–3 demo customers into static JSON for the app; don't read the CSV at runtime.
- Key fact the plan builds on: Utilities payments (342,728 rows, 4,922 customers) average ~€2,000/yr per customer (median ~€1,900) and have no `merchant_id` or `mcc_code`, so the bank can't tell what the contract is.
- Demo persona suggestion (not decided): ~35-year-old from Espoo with high bills and lots of restaurant spending.

## Mobile rules (demo device: iPhone, Safari and home-screen app)
- Design at 375–430px. The layout in `layout.tsx` is a 430px column, centred on laptops.
- Pad pages with `env(safe-area-inset-top/bottom)` (utilities `pt-safe`, `pb-safe`, or `calc(1.5rem+env(...))` when other padding applies). Fixed bottom bars need the bottom inset.
- Use `min-h-dvh` / `100dvh`, never `100vh`. Inputs stay at 16px or larger (iOS zooms on focus otherwise; `globals.css` enforces it).
- Tap targets at least 44px, no hover-only interactions, no popups or new windows (the app should work inside a webview).
- Chat: message list scrolls, input stays attached to the visible viewport above the keyboard. Test on a real iPhone; the Simulator is not available (no full Xcode on this Mac).
- Audio (ElevenLabs) must start from a tap on iOS. No haptics on iOS Safari.
- Never import `src/lib/demo.ts` from a client component (it is `server-only`; the build fails if you do). Compute on the server and pass small props.
- Installable: `src/app/manifest.ts`, icons in `public/icons/` and `src/app/apple-icon.png`. iPhone installs via Share, Add to Home Screen only (no prompt). Icon: white S from the logo on the slab green (#0c3524).

## Onboarding (first run), calendar and investing rules
- `/onboarding` runs once for a new user (`OnboardingGate` on Home redirects; "Skip for now" is remembered). Four steps: 1 your profile (accept it, or fix it with the small pencils: situation, income and payday, fixed bills), 2 savings goals, 3 investing, 4 your plan. Output: weekly spending budget, monthly transfer to a savings account, monthly room for investing, and what Solvo would move on payday (bills kept safe, irregular pot, savings, investing, spending account). The approved plan lives in localStorage (`src/lib/onboarding-store.ts`, cleared by Reset demo) and replaces the default EUR 200/month savings goal in Home's weekly numbers; the person's income and bill corrections flow through as `monthlyAdjust`.
- `src/lib/profile.ts` guesses student, studying and working, worker, part-time, between jobs or retired from the salary pattern and Kela's study grant (bank code "Opintotuki"; only real Nordea data has it, synthetic customers all come out as workers). `src/lib/schedule.ts` guesses payday and the usual day of rent and utility bills, and builds calendar events. `src/lib/plan.ts` is the allocation maths (rules of thumb at the top, every number traceable). All three are pure; the server pages send only the profile, usual dates and monthly numbers to the browser, never transactions.
- The calendar is part of the app at all times, not part of onboarding: Home has a "Coming up" card (next three weeks of money in and out, `src/components/upcoming-card.tsx`) and a Calendar button on the safe-to-spend card, both always shown. `/calendar` (reached from those): month grid with a "+" marker on days money arrives and a "-" marker on days it leaves. Tapping a day opens it in a sheet: what is expected (money in and out), for a day that has passed also what actually happened (loaded for that one day from `/api/day`, so the phone never holds the whole history), and "Add to this day" for the person's own expected income or costs (optionally monthly), stored in localStorage (`src/lib/calendar-store.ts`). There is deliberately no separate "add" button on the page. It uses the dates the person confirmed in onboarding when there are any.
- Bills have specific names, never a bare "Utility bill" where we know better. For the demo customer the names come from the e-invoices (`src/lib/bill-names.ts`: Electricity bill, Grid fee, Phone and internet, with the company shown beside it). For real bank data with merchant names, `billType()` in `src/lib/schedule.ts` names them from the company (Electricity bill, Grid fee, Phone and internet, Insurance, Water bill) and a recurring insurer becomes an Insurance bill. Pages build the schedule with `scheduleFor()` from `src/lib/schedule-server.ts`, not `inferSchedule()` directly.
- Phone testing: `npm run dev` works from a phone on the same Wi-Fi at `http://<your-mac-ip>:3000` (`next.config.ts` allows the machine's own network addresses in dev). Without that, Next's dev server serves the page but blocks its JavaScript, so nothing responds to taps. `npm run dev:live` stays on 127.0.0.1 on purpose and must never be opened from a phone.
- **The demo shows the real date, always.** The synthetic bank data ends on 2026-09-30 and all demo numbers, bills and reminders are built around that day as "today". `src/lib/demo-clock.ts` makes the app display the real date instead: it shifts every demo date by (real today minus 2026-09-30) days as it is formatted (`Intl.DateTimeFormat`), so 30 Sept shows as today and "due in 5 days" stays "due in 5 days". Data, sums and logic are untouched, and screens added later follow automatically if they format dates with `Intl.DateTimeFormat`. Rules: (1) every `page.tsx` must be `async` and start with `await connection()` (from `next/server`), because the clock reads the current time and Next must render per request, never freeze the date at deploy time; (2) code that shows REAL calendar dates (calendar, Coming up) must use `plainFormat()` from `demo-clock.ts`, never a bare `Intl.DateTimeFormat`, or its dates are shifted; (3) real dates need `toDemo()` before looking anything up in the demo data (see `/api/day` use in the calendar) and demo dates handed to the chat model go through `toShown()`; (4) Home's week strip and "days left" use the real weekday; (5) real Nordea data (once connected, see "Live Nordea" below) turns the shift off (`configureDemoClock(null)` in the root layout). Don't print raw demo dates (`c.asOf`) as text; format them.
- **Other banks (multi-bank view), opt-in and simulated.** Profile has "Other banks" with "Add another bank" (also an optional row in onboarding step 1). Nothing is assumed: a customer sees no other bank until they add one. Connecting Nordea shows a PSD2-style consent sheet and then attaches DEMO data from `src/lib/second-bank.ts` (a seeded generator: Nordea everyday and savings accounts, a side income S-Pankki can't see, insurance, gym, Netflix, Spotify, transfers between her own accounts and to Nordnet; plus a Nordnet portfolio). Nothing in it is real. The choice lives in cookies (`solvo_banks`, `solvo_view`, `src/lib/banks.ts`) because pages render on the server; Reset demo clears them. `src/lib/combine.ts` merges the banks into one customer and recomputes baskets and income; Home, plan, calendar, onboarding and the coach all read it through `getEffective()` / `getDemoEffective()` (`src/lib/source-banks.ts`). Home's "All your banks" card (toggle: All banks / S-Pankki only) shows cash and savings, investments, side income, subscriptions, insurance and money moved between her own accounts. Rules: transfers between a person's own accounts and deposits to Nordnet are saving, never spending; the coach prompt is built per request and gets a note on connected banks; real bank data (local Nordea mode) is never merged with the demo banks and never sent to a model (`getDemoEffective` is synthetic-only).
- **Live Nordea (the owner's real accounts, connected inside the app, local only).** `npm run dev:live` (= `SOLVO_LIVE=1 next dev -H 127.0.0.1 --experimental-https`) adds Profile > "Your real Nordea" > Connect Nordea. The person taps it, approves with Nordea ID and is back in Solvo; they never open Enable Banking's website. Flow: `POST /api/nordea/start` (random state token in an httpOnly cookie, asks Enable Banking for Nordea's approval URL) -> the bank -> `GET /callback` (state checked, single-use code swapped for a session, saved) -> `/connect/nordea` (downloads 535 days of transactions with a progress state, via `POST /api/nordea/sync`) -> Home shows the real Nordea. Profile then offers Sync now and Disconnect and delete (ends the consent at Enable Banking and deletes `data/private/` Nordea files). Code: `src/lib/enable-banking-core.ts` (JWT, calls; shared with `scripts/nordea-psd2.mjs`), `src/lib/live-nordea.ts` (guards, session, sync, disconnect), `src/lib/nordea-customer.ts` (transaction mapping, shared with `scripts/build-nordea-customer.mjs`), `src/lib/loopback.ts`. Rules, each one preventing a leak of real banking data: (1) every route refuses unless `SOLVO_LIVE=1`, not on Vercel, `Host` is localhost/127.0.0.1/[::1], and POSTs carry a same-origin `Origin`; the routes answer 404 when off, so the public app shows nothing; `/api/day` also refuses non-loopback hosts when it serves real data; (2) the app must be opened at the registered redirect host (`https://localhost:3000`, env `ENABLE_REDIRECT_URL`), or the state cookie does not come along and `/start` says so; (3) real data is never merged with the demo banks, never sent to a model (`getDemoEffective` stays synthetic-only), never printed in logs or error messages (counts and dates only); (4) `ENABLE_APP_ID`, `ENABLE_KEY_PATH` (key kept outside the repo), the session and all downloaded files stay in `.env.local` and gitignored `data/private/`; (5) the consent is account-information only, 30 days by default (`NORDEA_CONSENT_DAYS`, max 180), and there is no payment call anywhere. The first `npm run dev:live` asks to install a local certificate (mkcert, may ask for the Mac password); the application's redirect URL must be exactly `https://localhost:3000/callback` in Enable Banking's control panel. Tested end to end against a mock Enable Banking server only: the real Nordea approval needs the owner's Nordea ID. After the event: Disconnect in the app, delete the app in Enable Banking's control panel, delete the .pem and `data/private/`.
- **Subscriptions are their own bracket** (category "Subscriptions", basket 1, fixed and regular): Netflix, Spotify, a gym. Insurance is basket 1 too. Real bank data gets them from merchant names (`scripts/build-nordea-customer.mjs`); the calendar lists any named payee charged the same amount about monthly. S-Pankki's synthetic data has no merchant names, so it shows none until a bank that names merchants is connected.
- **Nordnet facts (checked 14 Nov 2026).** Not in Enable Banking's bank list for FI, SE, NO or DK, so no PSD2 route. Nordnet's own External API (docs at nordnet.fi/externalapi/docs) is a trading API with read endpoints for accounts, balances (`/accounts/{accid}/info`) and positions. Its getting-started page says it is "currently not onboarding new customers" and its examples README says to contact Nordnet Trading Support, yet the same page describes adding an API key in the customer's own profile (My pages, Settings, My profile, Security). Whether a given account can get a key is unverified: only trying tells. The read-only, owner-only, local connector is `src/lib/nordnet-core.ts` plus `scripts/nordnet-api.mjs` (setup steps in the script header): Ed25519 login signed exactly like Nordnet's official `sign.py`, then GET-only reads. `isAllowed()` refuses every other call, so it cannot place an order. Offline tests with a throwaway key pass; it has NOT been run against a real Nordnet account. Output goes to `data/private/nordnet-api/` (gitignored) and shows on Home only in local Nordea mode (`LiveNordnetCard`). The demo's Nordnet is simulated. For people without API access the real paths are deposits visible as transfers in bank data (already handled) and an export file they share; do not build a file parser from a guessed format, get a real masked sample first.
- One look for money moving, everywhere: use `MoneyBadge` and `SignedAmount` from `src/components/solvo/money-badge.tsx` (money out = warm circle with a minus, money in = green circle with a plus; the sign carries the meaning, not only the colour). Other shared bits: `Sheet` (bottom sheet for small edits), `NumberField` and `Stepper` (`fields.tsx`; NumberField keeps raw text so a field can be emptied and retyped, never use a controlled type=number input), the pencil `EditButton` pattern in the onboarding client. All tap targets 44px.
- Investing: Solvo never recommends a product. It sizes a budget ("room to invest": half of what is left after bills, buffer and goals, zero before a starter buffer or while between jobs) and `src/lib/fund-match.ts` screens a catalogue by the person's stated safety, horizon and "environmentally friendly" wish, showing only standard facts (1-7 risk class, EU SFDR label, fee). The person can save funds as interesting and "Start saving" opens the fund's page; nothing is bought. No ranking, no "best", no wording like "we recommend". Keep disclaimers short.
- Property goal: the goal is "Home or property" (a home, a cabin, anything bought with a down payment), not ASP specifically. ASP is only a pointer for first-home buyers: its rules changed in June 2026 and sources disagree on eligibility, so the app states no age limits, saving periods or percentages. Do not add any without a checked source.
